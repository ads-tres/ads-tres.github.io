Ethio Heran tutoring platform

Ethio-Heran PLC, lead software engineer

Runs a home-tutoring company end to end: hiring tutors, scheduling, attendance, parent billing, payroll and staff exits. It replaces spreadsheets, paper forms and phone calls spread across departments with one system built for Ethiopia, including the Ethiopian calendar and bilingual SMS.

The problem

A tutoring business runs on hundreds of small events: sessions held, reports submitted, payments collected, tutors hired or leaving. Each one affects money or a family’s experience, and each belongs to a different department with different access rights. Done by hand, attendance gets approved late, pay is miscalculated and reports go missing.

How it fits together

  1. Filament panels
  2. Livewire
  3. Service classes
  4. Eloquent
  5. MySQL
  • Each role works in Filament admin screens built on Livewire, so every click is a server round-trip with no separate front-end API to keep in sync.
  • Screens stay thin and call service classes that hold the business rules, which read and write MySQL through Eloquent inside database transactions.
  • A scheduler running on Addis Ababa time drives the background work: attendance gap checks, report and payment reminders, finance reports and the messaging outbox.
  • The outbox is a database table. A cron job sends its messages through the SMS gateway, email and the Telegram Bot API within a fixed time budget and records delivery per recipient. Question papers come from the Gemini API, falling back across models when one is busy.

Key decisions

  • Ledgers rebuild from source records, so attendance approved late still reaches billing and pay, and corrections are new entries that keep history auditable.
  • Access is checked three ways: role permissions, a policy per resource, and configurable rules for who may message whom.

The problem

Running a separate site for every brand multiplies hosting, fixes and admin work. Adding a brand here is configuration and theming, not a new build, and every brand shares the same booking, payment and admin tools.

How it fits together

  1. Blade + Alpine.js
  2. Brand middleware
  3. Service layer
  4. Eloquent + global scopes
  5. MySQL + Redis
  • Pages are server-rendered with Blade and work without JavaScript; Alpine.js adds interactivity on top. Staff use a Filament and Livewire admin.
  • Each request first passes middleware that identifies the brand from the hostname. A theme manager routes it to that brand’s handler, which calls a service layer over MySQL, with Redis for caching.
  • Global query scopes add the brand filter to every query, so no developer can forget it. Queries return no rows without a brand, and saves are validated too.
  • Payments are server-authoritative: the browser goes to Stripe Checkout, but only a signature-verified, idempotent webhook with row-level locking can mark money as received, so each payment counts once.

How the numbers were reached

  • Tour cards used to look up their data one by one. Batched loading keeps the listing at a constant 4 or fewer queries, and a test fails if that number grows.
  • Every push to main runs migrations, asset builds, cache warm-up, service reloads and queue restarts automatically.

The problem

Front-desk staff need to register members, sell plans and check people in quickly, while members want to renew and pay from their phone. Each gym must only ever see its own members and money.

How it fits together

  1. Staff panel / Flutter app
  2. REST API v1 + Sanctum
  3. Services
  4. PostgreSQL
  • Two front-ends share one versioned REST API: a Filament staff panel for the front desk and the Volt Flutter app for members. Both authenticate with Sanctum tokens.
  • Requests are scoped to the member’s gym and stored in PostgreSQL, where composite foreign keys stop records from linking across gyms.
  • Chapa sends payment confirmations to a webhook, which activates the membership. AfroMessage delivers SMS sign-in codes, renewal reminders and announcements.
  • The whole stack runs in Docker, and GitHub Actions runs the Pest tests, Larastan and Pint on every push.

How it fits together

  1. Flutter app
  2. Dio + Sanctum
  3. Laravel REST API
  4. PostgreSQL
  • Landlords sign in with an SMS one-time code. The code is hashed and rate-limited, and a valid one returns a Sanctum token.
  • The Flutter app (Riverpod, Dio, go_router) sends that token with every request to the Laravel API, which scopes every query to the signed-in landlord.
  • PostgreSQL stores tenant ID numbers encrypted, with consent records, to meet Ethiopia’s data-protection law.
  • The API enforces the rental directive itself: a two-year minimum lease, a yearly rent-cap check and late flags, so the rules hold whatever client calls it.
